# Prototype: constraint-expression dynamic config

**Status: prototype, for evaluation.** Nothing here is on by default. With
`expressionFilepath` unset, dynamic config behaves exactly as it does today.

## The problem

Today a dynamic config value is selected by exact-equality match against
`dynamicconfig.Constraints` (`common/dynamicconfig/client.go`), a closed struct of eight
fields, scanned in a precedence order generated by `cmd/tools/gendynamicconfig`. Three
things follow:

1. **New dimensions need code.** Rolling a setting out by deployment zone, cluster, host,
   deploy ring, or task queue partition index means adding a field to `Constraints`, adding a
   precedence order to `gendynamicconfig/main.go`, regenerating `setting_gen.go` (1972 lines),
   and extending `yaml_loader.go`. There is no configuration-only path.
2. **No boolean logic.** A value's constraints are a conjunction of exact matches.
   `env = staging AND (zone = us-west-1 OR zone = us-west-2)` cannot be written. Percentage
   rollout exists only as bespoke side channels (`rollout.go`, `gradual_change.go`).
3. **A call site sees only its own precedence tier.** A task-queue-precedence setting can be
   constrained by namespace, task queue name, and task queue type, and by nothing else, ever.

## What was built

[github.com/davidporter-id-au/configurator](https://github.com/davidporter-id-au/configurator)
inverts the model: config is a default plus an ordered list of DSL overrides, and the caller
supplies an open `map[string]any` of constraints evaluated at read time.

It is vendored at `common/dynamicconfig/configurator/` (see the README there for why it
cannot be a `go.mod` dependency yet), and integrated in two layers.

### Layer 1: an `Evaluator` inside `Collection`

The natural-looking seam, implementing `dynamicconfig.Client`, is the wrong one:
`GetValue(key) []ConstrainedValue` requires the backend to pre-enumerate every matching
combination so that `Collection` can do the equality match itself, and an open constraint
space cannot be enumerated.

Instead the hook is `matchAndConvert` (`common/dynamicconfig/collection.go`), the choke point
every read already passes through with its constraints in hand:

```go
type Evaluator interface {
    Has(key Key) bool
    Eval(key Key, base Constraints, extra map[string]any) *ConstrainedValue
}
```

- `Eval` returns a raw, unconverted value, so the existing converters (`convertInt`,
  `convertDuration`, `ConvertStructure`, …) run unchanged and Temporal's lenient coercion and
  deep-copy-merge semantics are preserved.
- The returned pointer is stable for the lifetime of a config generation, so `Collection`'s
  weak-pointer conversion cache works exactly as it does for `Client` values.
- Constraints are merged from three sources: process-ambient (`env`, `zone`, `cluster`,
  `service`, `host`, `serverVersion`, plus arbitrary operator-defined keys), the setting's own
  precedence (`namespace`, `taskQueueName`, `shardID`, …), and ad-hoc (layer 2).
- All ~677 settings are covered, and no consumer of a property fn changed.

### Layer 2: ad-hoc dimensions via `Collection.WithConstraints`

Property fns take no `ctx`, so request-scoped constraints cannot be threaded through them.
Instead `WithConstraints` returns a cheap read-only `Collection` view carrying extra
dimensions, built once per long-lived component.

`service/matching` uses it to expose dimensions that have no `Constraints` field:
`taskQueuePartitionID`, `taskQueueKind`, `taskQueueIsRoot`, `taskQueueIsSticky`. Three
settings are resolved through it as a demonstration
(`getTasksBatchSize`, `syncMatchWaitDuration`, `maxWaitForPollerBeforeFwd`).

`maxWaitForPollerBeforeFwd` is the sharpest example: it governs forwarding, which only
non-root partitions do, and root-ness is a distinction the task queue precedence order simply
cannot draw.

## Results against the four goals

### (a) Arbitrary constraint dimensions — confirmed

`config/dynamicconfig/expressions-demo.yaml` targets `env`, `zone`, `service`, a custom
`deployRing`, and four task-queue-partition dimensions. None of the eight is expressible
today; all eight are configuration-only here, with no code change and no codegen.

### (b) Boolean logic — confirmed, with gaps

`=`, `!=`, `>`, `<`, `and`, `or`, and parenthesised nesting all work. Missing, and each one
came up while writing the demo config:

| Missing | Why it matters |
| --- | --- |
| `>=`, `<=` | `"sdkVersion" >= 2` has to be written `> 1`, which is wrong for floats |
| `in` / set membership | zone lists become long `or` chains |
| `not` | no way to write "everywhere except" |
| prefix / regex | Temporal already needs this: `ConvertWildcardStringListToRegexp` |
| percentage rollout | **a real regression**: `gradual_change.go` and `rollout.go` provide stable-hash cohorting and time-phased ramps that the DSL cannot express at all |

The last row is the significant one. `matching.useNewMatcher` and
`matching.enableFairness` are shipped as `GradualChange` rollouts today, so the DSL is not
yet a superset of what the current system does.

### (c) Authoring ergonomics — better for logic, not obviously better for simple cases

Today, "250 in staging us-west-1 and us-west-2, 100 in the canary namespace" is not
expressible at all. The nearest approximation needs one entry per combination:

```yaml
matching.getTasksBatchSize:
  - value: 100
    constraints: {namespace: canary}
  - value: 1000
    constraints: {}
# ... and no way at all to say "us-west-1 or us-west-2 in staging"
```

versus:

```yaml
matching.getTasksBatchSize:
  defaultValue: 1000
  overrides:
    - matchString: '"env" = "staging" and ("zone" = "us-west-1" or "zone" = "us-west-2")'
      matchResult: 250
    - matchString: '"namespace" = "canary"'
      matchResult: 100
```

Two honest caveats. For the common case of a single unconstrained value, the current format
is terser (`key: [{value: 100, constraints: {}}]` versus three lines). And the DSL's
mandatory quoting of keys inside a YAML-quoted string (`'"env" = "staging"'`) is awkward and
easy to get wrong.

Ordered-first-match is also a genuine improvement over the implicit precedence table: what
wins is visible in the file rather than in `gendynamicconfig/main.go`.

### (d) Performance — free when unused, ~4.5x when used

`go test ./common/dynamicconfig/ -bench BenchmarkEvaluator -benchmem` on an M5 Max:

| Case | ns/op | B/op | allocs/op |
| --- | --- | --- | --- |
| no evaluator (today's path) | 51.5 | 0 | 0 |
| evaluator present, key absent | 52.6 | 0 | 0 |
| expression, 0 overrides | 228.8 | 48 | 3 |
| expression, 1 override | 238.8 | 48 | 3 |
| expression, 5 overrides | 266.4 | 48 | 3 |
| expression, 20 overrides | 265.1 | 48 | 3 |
| expression, 5 overrides, `WithConstraints` view | 312.7 | 48 | 3 |

The row that matters most is the second: the `Has` guard is one lookup on an interned key, so
the ~677 settings nobody configures by expression pay ~1 ns and zero allocations. That was the
main risk and it did not materialise.

For keys that *are* expression-configured, reads cost roughly 4.5x the current path. The cost
is dominated by building the constraint map, not by evaluating expressions: scanning 20
overrides instead of 0 adds only ~36 ns. Pooling the map (`constraintMapPool`) cut this from
304 ns / 712 B / 7 allocs to the numbers above; the remaining 48 B is boxing string and int
constraint values into `any`.

At ~230 ns a read this is fine for anything read per request, but it is not free, and today's
path is genuinely fast. A production version would want to memoize per (key, constraint-set).

## Problems found in the library

1. **The module path does not match the repo URL.** `go.mod` declares
   `github.com/davidporter-id-au/constraints-config`; the repo is `.../configurator`, so
   `go get` cannot resolve it. This is why the code is vendored. It also has no tags.
2. **`LoadKey` races with `Eval`.** `internal/library/impl.go` writes `c.loads[key]` on a bare
   map while `Eval` reads it, so registering a new key concurrently with reads is a data race.
   Updating an existing key is safe. Worked around by building a fresh `Configurator` per
   reload and swapping it behind one `atomic.Pointer`; the library is never mutated while live.
3. **No change notification.** Supplied here by the adapter, reusing Temporal's existing
   mtime-poll and subscription plumbing.
4. **`Eval` decodes on every call in the obvious usage.** Avoided by having the library resolve
   an *index* into a table of pre-decoded values, which also gives the stable pointers that
   `Collection`'s conversion cache needs. This is a nice pattern but not an obvious one, and it
   is only possible because the adapter controls the config fed to `LoadKey`.

## Known limitations of this prototype

- **Subscriptions on derived views.** `WithConstraints` returns a read-only view; `Subscribe`
  on it will never fire. Root collections are unaffected.
- **Layer 2 covers three matching settings**, not all of them. Extending it to every setting
  would mean re-resolving the whole of `Config` per task queue.
- **Expression config wins over constrained defaults.** Deliberate, but it means a
  `NewTaskQueueIntSettingWithConstrainedDefault` value is overridden by an expression default,
  which is arguably surprising.
- **No metrics.** The file based client reports `DynamicConfigUpdateFailure`; the evaluator only
  logs.

## Recommendation

The constraint model is the right one, and the integration point (`matchAndConvert` plus an
optional `Evaluator`) is small, reversible, and cheap enough to leave permanently in place.
The open constraint map solves a real problem: the closed `Constraints` struct is the reason
Temporal cannot roll anything out by zone, host, or partition without a release.

Two things must be resolved before this could be more than a prototype:

1. **Percentage and time-phased rollout must exist in the DSL**, or the DSL must compose with
   `GradualChange`. Without it this cannot replace what matching already relies on.
2. **The library needs a fixed module path, a tag, and the `LoadKey` race fixed** before it
   can be a dependency rather than a vendored copy.

Beyond that, `>=`/`<=`, `in`, and prefix matching are the operators that were actually missed
in practice, and per-lookup memoization would close most of the performance gap.

## Trying it

```bash
# validate an expression file offline
go run ./cmd/server validate-expression-config config/dynamicconfig/expressions-demo.yaml

# unit tests, benchmarks
go test -race ./common/dynamicconfig/... ./service/matching/
go test ./common/dynamicconfig/ -run XXX -bench BenchmarkEvaluator -benchmem
```

To run a server with it, add to the `dynamicConfigClient` block of a config file:

```yaml
dynamicConfigClient:
  filepath: "config/dynamicconfig/development-cass.yaml"
  pollInterval: "10s"
  expressionFilepath: "config/dynamicconfig/expressions-demo.yaml"
  expressionConstraints:
    env: "staging"
    zone: "us-west-2"
    deployRing: 2
```

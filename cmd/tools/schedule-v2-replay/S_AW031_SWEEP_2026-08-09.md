# s-aw031 Schedule V1 versus CHASM replay sweep

## Executive summary

This sweep read saved Schedule V1 workflow histories from `s-aw031` and replayed their external
inputs against fresh, in-memory CHASM schedulers. It did not update, signal, pause, migrate, or
delete a live schedule.

After correcting carried-workflow identity mapping and replacing wall-clock timeouts with bounded
virtual work, the 91 saved histories classify as follows:

| Classification | Before | After | Interpretation |
| --- | ---: | ---: | --- |
| `match` | 16 | 16 | Compared action decisions, requests, counts, and final state match. |
| `timing_only` | 22 | 25 | The same workflow IDs were started at different observed times. |
| `significant` | 13 | 9 | A request, nominal occurrence, action count, or final state differs. |
| `inconclusive` | 0 reported / 9 external timeouts | 10 | Replay exceeded a virtual-work budget. |
| `unsupported` | 31 | 31 | The saved history lacks usable Schedule V1 initialization state. |

The identity fix cleared three previously significant, high-volume continue-as-new histories:
they now start the same 235, 285, and 306 workflows as V1 and differ only in observation time. A
fourth previously significant case is now correctly bounded as inconclusive. The nine remaining
significant cases are narrower candidates, but completion-driven cascades mean they are not nine
independent scheduler defects.

Production identifiers are omitted. Case references below are stable truncated hashes from the
redacted rerun. Raw histories, the unredacted report, and the identity crosswalk remain outside the
repository in an owner-only temporary directory.

## Fidelity corrections and what they changed

### Carried workflow/run identity

A continued V1 scheduler run can begin with workflows already running. Migration-state conversion
preserves those workflow and run IDs in CHASM buffered starts, but the old oracle initialized its
identity map as empty and learned identities only from new starts. It therefore could not apply a
completion for a workflow carried across the run boundary. Under `SKIP` or buffering policies, the
apparently running workflow then blocked later actions and created a false missing-action cascade.

The replay now seeds exact workflow/run mappings from incomplete migrated buffered starts. New
starts are also mapped by workflow and run ID rather than workflow ID alone. A completion with no
run ID is accepted only if it has exactly one candidate; ambiguity is reported as inconclusive.

This correction moved three production histories from significant to timing-only. It does not
force a V1 completion onto a different CHASM nominal occurrence: if CHASM genuinely did not emit
the corresponding workflow ID, the completion remains pending and the occurrence difference is
retained.

### Deterministic replay budgets

The original sweep killed nine histories after 15 wall-clock seconds. That measured machine speed
and left no structured evidence. Replay now defaults to per-history limits of 10,000 virtual
deadlines, 100,000 CHASM tasks, and 10,000 starts. All ten bounded cases reached 10,001 deadlines;
nine produced no actions and one produced a single matching action before the limit. They are
`inconclusive/replay_budget_exceeded`, with counters, and do not receive fabricated missing-action
findings from partial output.

The ten cases belong to one namespace and appear to combine dense schedules with a long sparse
history horizon. Raising the limit is possible for targeted profiling, but is unnecessary for a
broad sweep and can make runtime scale with virtual occurrences rather than history size.

### Payload-safe request diagnostics

Report version 3 explains request mismatches without decoding customer payloads. It records field
presence, element counts, payload encodings, reserved scheduled-time values, failure-info types,
and deterministic digests in the restricted unredacted report. Default redaction removes digests
and identifiers. Raw payload values and failure messages are never copied into either report.

## Remaining findings

### Scheduled-start timestamp precision

One case has 57 `search_attributes` mismatches. All 57 are
`TemporalScheduledStartTime`: V1 records a whole-second value while CHASM retains a sub-second
value. Two more instances occur in another significant case. This confirms in production data the
controlled-corpus behavior documented in [DIVERGENCES.md](DIVERGENCES.md).

First-pass triage:

- **Compatibility impact: Low.** Workflow code or visibility queries can observe the timestamp
  precision change, but action identity usually remains unchanged.
- **V2 bug likelihood: Low.** CHASM preserves more precise time; V1 couples this field to its
  whole-second workflow-ID convention.
- **Confidence: High.** The safe diagnostic decodes only the reserved datetime field.

The same case also retains one paired missing/duplicate workflow ID while preserving 56 total
starts and an action count of 422. That occurrence-identity difference is independent of timestamp
precision and remains a medium-impact compatibility candidate.

### Completion result and continued failure propagation

Across significant cases, request diagnostics report:

| Field | Mismatching starts | Observed structure |
| --- | ---: | --- |
| `last_completion_result` | 36 | Presence/count or deterministic payload digest differs. |
| `continued_failure` | 750 | Failure presence or top-level failure-info type differs. |
| `search_attributes` | 59 | All identified safe differences are scheduled-time precision. |

The 750 continued-failure count is dominated by three chained interval histories: 719 requests
carry a CHASM timeout failure where V1 carries none. This is not 719 independent defects. Once the
first nominal occurrence diverges, a V1 completion cannot be applied to a CHASM workflow that was
never started; CHASM retains its own prior outcome, and later request comparisons inherit that
state. Similar causal contamination applies to later missing-action and action-count findings.

Twenty mismatches instead have a V1 activity failure and no CHASM failure, eight have the reverse,
and three have a CHASM termination failure where V1 has none. The first mismatch in each chain is
the useful unit of investigation. The 36 last-completion-result mismatches occur in one calendar
schedule and deserve a focused controlled reproduction because workflow behavior may consume that
value.

First-pass triage:

- **Compatibility impact: Medium if the first mismatch survives isolation.** Completion input can
  change workflow behavior.
- **V2 bug likelihood: Undetermined.** The report now proves which structural component differs,
  but later mismatches are downstream of earlier action/completion divergence.
- **Required determination:** reproduce the first mismatch with one prior completion and inspect
  V1-to-migration-state conversion versus CHASM invoker outcome selection.

### Nominal occurrence selection

Eight of nine significant histories retain missing or extra workflow IDs. In seven of them, an
unmatched completion is followed by a lower CHASM action count; the first missing/extra pair is the
candidate and subsequent differences may be its cascade. The pattern is consistent with the
controlled `SKIP` boundary difference: V1 generates elapsed occurrences during a delayed workflow
task, while CHASM resolves overlap at exact virtual deadlines.

One illustrative case has one V1 workflow at nominal `01:30` and one CHASM workflow at `03:00`.
The V1 completion cannot safely be applied to the different CHASM execution. Retaining it as
unapplied is intentional oracle behavior, not the old carried-identity bug.

First-pass triage:

- **Compatibility impact: Medium if confirmed.** A different nominal occurrence changes workflow
  ID and cadence.
- **V2 correctness-bug likelihood: Low to undetermined.** Exact-deadline behavior can comply with
  the overlap contract while differing from V1 workflow-task coalescing.
- **Next evidence:** build a first-divergence timeline for each case using nominal deadlines,
  workflow completion time, pause/update inputs, and overlap policy; ignore downstream cascades
  after the first unmatched occurrence.

## Overall determination

The corrected harness concretely removed known false positives: three formerly severe cases now
compare the same hundreds of starts, and expensive cases are explicitly inconclusive rather than
timeouts or partial mismatches. The remaining evidence supports three real compatibility topics:
scheduled-time precision, first-occurrence selection around completion/pause/update boundaries,
and completion-result/failure propagation.

It does not yet establish nine independent V2 bugs. Investigation should start at the first
divergence in each history and stop comparing dependent requests after an unmatched occurrence.
The highest-value next controlled test is the 36-start last-completion-result case, followed by
deadline timelines for the first unmatched `SKIP` occurrences.
